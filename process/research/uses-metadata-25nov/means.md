# The means by which a module and its tests depend on an earlier module, and what a uses file must say (25 Nov 2026)

Status: research for PROCESS #15, by a worker. Nothing changed. Read at origin/main 4acec19. For the owner's proposal in
`../uses-metadata-25nov.md`: each module keeps a job-written file of the providers and entries it and its tests use.

How sure: **read** means read in the code or a cited record; **measured** means a number from a civicsmith reading or
report, with its source; **inference** means reasoning, not shown; **unmeasured** means nobody has counted it.

## Summary and bottom line

1. **Thirty-one means, in five families** (section 1): imports (A, 11 means), values and kinds handed across without an
   import of the provider (B, 7), calls and data by name (C, 5), files, programs and shared state outside the language
   (D, 8), and one that is not a use (E). A job can record every one of them, because it wrote or read the code. Two it
   can record only as a pattern, not a list: run-time walks and loaders whose set of modules grows with the product.
2. **Only family A has a route the tool can check.** For imports the existing declared-uses check (design part 2 §6) can
   compare the file with the code both ways. For B the language reader can confirm a record only where the values are
   typed (most of civicsmith's are not). For C it can confirm one only where the carrier marks of build text 2b §5 are
   written. For D nothing in the tool sees the use, so the record is the job's word alone. A forgotten record is a missed
   notice, which the design accepts. It is caught by the user's own tests or a walk.
3. **Half the design is on the provider's side.** A record tells its user only if the provider's statement of what
   changed can name the same entry. Today's listing names exports, operations (`op:`), tables (`table:`) and
   `@message` kinds. It has no entry for a module's data file, fixture, source text, program, global name, registry
   key, config key or generated output. Without one, every D record and most C records tell nobody. Each provider
   must list such entries in its own file, and its job must say when one changed.
4. **Every record needs five things**: provider; entry, spelled as the provider spells it (`<file>:<name>` where two of
   its files export one name, as for civicsmith's five `generate`); direction (it accepts, it hands back, or both);
   route (import, own name, imports map, re-export through R, dynamic, computed loader through H, handed by Q's entry,
   callback, by name through carrier C, by path, global, message, generated by G); and where (code, tests or both,
   with the files). Section 2 gives the form.
5. **What the tool can follow today** (section 3):
   - **It follows**: relative, default, namespace and literal dynamic imports; `require` of a written path; re-exports
     (to the declaring module); JSDoc kinds; typed value flow, members included; and calls by name where marked.
   - **It cannot read**: own-name and `#` imports, in the staged scan; computed imports; values of unknown kind. In
     each case it tells the user as not followed, often for every provider (F2, F3).
   - **It does not see at all**:
     - a sibling package's name in a product with no root `package.json`. Every reader treats it as outside the product.
     - `#` imports, in the check.
     - caught errors, which are deliberately counted as outside the product.
     - files, programs, globals, registries, messages, generated code and copies.
   - **It misses** an own-name passer (M1), and a real change hidden under "anything" (M2).
6. **civicsmith** (section 4):
   - Its imports are clean: 6,016 cross-module static imports, all to earlier, declared modules.
   - What it depends on beyond imports is large:
     - 1,279 module pairs referred to and not declared, none by import;
     - 5,350 references to later parts, 3,884 of them from code;
     - 19 whole-tree walks;
     - 62 test files that boot plane;
     - computed loaders: test-support's helper imports 95 later parts, and 341 computed references are still open;
     - 1,068 operations called by name, of which the UI names 560;
     - passers: 164 listings, then 90, changed "through" setup-words.
   - Imports by its own name or by `#`: **unmeasured**. The tool's own-name resolver keys on a root `package.json`,
     which civicsmith did not have on 21 Nov (11 packages, no root).
7. **The owner's premise holds for civicsmith's imports, not for the rest.** He wrote that every reference was written
   with knowledge of providers earlier in the order. All 6,016 imports point earlier. But thousands of path references
   point later, and walks find their modules at run time. A uses file cannot record those as legal uses. It would bring
   them up as order faults for ARCH (the refactoring plan's work), not absorb them. Until they are moved, the file is
   complete only for what the order allows.
8. **Indirect use (section 5). Recommended: option C, "origin keyed".**
   - U's file names P's `Row` as the entry it uses, with "via Q's `rows`" as its route. U also names Q's `rows`, which
     it calls.
   - Q's own file says "`rows` hands on P's `Row`".
   - A change to `Row` tells the modules that read or build `Row` and does not propagate through Q's users.
   - This is the owner's "users of the entry that changed" taken literally. It removes the F5 multiplier, which is a
     sum over passers' users, and leaves at most one told job per passer.
   - It stays accurate through the existing rule: when Q changes where `rows`' value comes from, that is a change to
     what `rows` hands back, which tells U, whose job then updates the record.

## 1. The means

Granularity: **provider** is the whole module; **entry** is one entry of the provider's listing (an export, an operation,
a table, a class or handle member); **member** is a field or method inside a plain data kind. Members are finer than
the listing's comparison and finer than the owner's rule, which tells by entry. "Can the job record it": always "yes"
unless said, because the job wrote the reference or reads it.

Notes on the table:

- **Order.** By design part 2 §1 every recorded provider must stand before the user. A record of a later module, an A11
  pattern that walks later modules, or a D3 boot of a later module (civicsmith's plane) cannot be made legal by writing it
  down. The job reports it to ARCH, as the check already does for a declared later use.
- **Domain or range.** The owner's rule treats the two differently: accepting more tells no one, and any change in what
  is handed back tells. A user that only receives (B1, B6) is not concerned by what P accepts, and a user that only
  hands in (B5) is not concerned by what P hands back. Recording the direction lets the lookup apply that. (Inference:
  today's tool tells by entry without direction.)
- **Members.** The owner's rule tells by entry. Fields read (`row.name`) are worth recording only as data for the told
  job's related tests, unless the owner chooses member-level telling.

## 2. What each record must carry, and the provider's half

**A record** (one per provider, entry, direction and route; JSON or lines, a form to design):

```
provider:  setup-words
entry:     word                  # as the provider's own file names it; <file>:<name> where needed;
                                 # op:x, table:x, file:<path>, program:<path>, message:<kind>, global:<name>, registry:<key>
direction: hands back            # accepts | hands back | both
route:     via q:rows            # import | own name | imports map | re-export via R | dynamic | computed (file:line)
                                 # | via helper H | via Q:entry | callback | by name via C | by path | config | global
                                 # | message | generated by G | copy | pattern
where:     code+tests            # code | tests | both, with the files (the owner's words: "in the module code, tests, or both")
```

**Patterns.** One record for a walk or registry: `pattern: every module before me, entry DECLARED_OPS`. The lookup
expands it against the module list at the moment of the notice. So the record does not go stale when modules are added,
and a walk over later modules is refused as an order fault.

**The provider's half.** A record tells only if the provider's change statement can name the same entry. Today's listing
has entries for exports, `op:`, `table:` and `@message` kinds (build text 2b §5-6). For D1-D8 and C4-C5 each provider's
file must also list the non-code entries that other modules may use:

- public data files, fixtures and schemas;
- programs, with their messages;
- globals and registry keys it sets;
- config names;
- generated outputs.

Its job must then say, at each change, which of them changed. Some of these have no "domain or range" (a fixture's
contents, a word row's text). The owner's rule then needs one sentence: is a changed data file, or a changed row of a
table such as `word`'s, a change to what the module hands back? A rule question for the owner, not answered here.

**Hands-on lines.** A module that hands on another's kind or value (a passer, a re-exporter, a helper that loads modules
for its callers) says so in its own file: `rows hands on p: Row`, `re-exports p: x`, `carrier: loads modules its callers
name`. These lines do three things:

- they let a user's job find an origin from files, not by reading Q's code;
- they let the tool cross-check the user's `via q:rows` against Q's line, file against file;
- a change in Q's line is a change to what Q's entry hands back, which tells Q's users (section 5).

**What can be checked.** For an import route (A1-A8) the existing check can compare the file with the imports it sees,
both ways, as it compares declared uses now. It reads written paths, `require` and the root package's own name. For a
B route the language reader can confirm the record where the values are typed (`usage.mjs` resolves `row.name` to P's
`Row`). For a C route the carrier reader can confirm it where the marks are written. For a D route nothing can check
it.

A cheap, non-refusing help for the job (inference; `module-uses-23nov.md` option C, there as a refusal):
- list the path strings that point into another module's folder;
- list the computed imports;
- list the `spawn`, `Worker` and binding arguments;
- the job then confirms each is recorded.

## 3. What the current tool can and cannot follow

Three readers, each with its own idea of an import:
- the check (`check.mjs`, declared uses);
- the notice's usage reader (`usage.mjs`, entries, through TypeScript);
- the staged scan and the narrowing (`staged.mjs`, `narrow.mjs`, regular expressions over the text).

Marks:
- **✔** followed;
- **~** partly;
- **U** "cannot follow". The scan calls it unreadable, so the user is opaque or not followed, and is told for every
  provider (F2, F3);
- **—** silent: not seen, and no telling follows from it.

## 5. Indirect use: U reads fields of P's `Row` received from Q

The case: Q's `rows()` hands back P's `Row[]`, and U reads `row.name`. U never imports P. `Row` changes, and the owner's
rule tells "the users of the entry that changed". Today, if Q states `rows`' kind, the usage reader already resolves
`row.name` to P's `Row`, so U is a user of `Row`. Q's listing also changes "through" P, so every user of Q's `rows` is
told too (F5). If Q is untyped, U is not followed and is told as such (F2), or missed (M2).

U's file names Q's `rows` in every option, because U calls it. The question is whether P's `Row` is named too, and
which name a change to `Row` looks up.

### Option A. Q's entry only ("hop keyed")

U's file names `q: rows`. A change to `Row` reaches U only by propagating: Q's `rows` counts as changed because it
hands on `Row`, and everyone who names `q: rows` is told.

- **(a) Who is told.**
  - Every user of `q: rows`, whether it reads `Row`'s fields or only counts the rows or passes them further.
  - And their users in turn, where they hand it on again.
  - Strictly, Q's range did change, so this follows the letter of "range". It is not "the users of the entry that
    changed". It is what told 197 for 1356.
- **(b) Keeping it accurate.** The easiest for the job: it records only what it calls. The difficulty moves to the
  propagation, which needs Q to state what `rows` hands on (Q's file, or Q's listing as now). Where Q is untyped and
  has no such line, a real change to `Row` reaches nobody past Q.
- **(c) Passers multiplier.** Full: told = the sum, over passers, of their entries' users, repeated at each level.
  Measured on civicsmith: 164, then 90, listings changed through setup-words.

### Option B. P's `Row` only ("origin only")

U's file names `p: Row`, not how it got there. It still names `q: rows` as a call, but not as the route of `Row`.

- **(a) Who is told.** Exactly the modules that read or build `Row`: U, other readers, and Q only if Q itself reads
  or builds `Row`. No propagation.
- **(b) Keeping it accurate.** The job must find the origin of every kind it reads. Where values are typed, the reader
  does that already. Where they are untyped (most of civicsmith), the job reads Q's code. U's record goes stale when Q
  changes where `rows` gets its values, while U's code stays the same, and nothing links the two. U would keep a record
  of `p: Row` while reading `r: Item`. A missed notice follows, and a needless one too.
- **(c) Passers multiplier.** None.

### Option C. Both, keyed on the origin (recommended)

U's file names `p: Row` (hands back) with route `via q: rows`, and names `q: rows` as its own use. Q's file names
`rows hands on p: Row`. A change to `Row` tells the modules whose files name `p: Row`. It does not propagate to Q's
other users.

- **(a) Who is told.**
  - As B: every reader or builder of `Row`, wherever it got it.
  - Q, as a pure passer, gets one notice at most. The owner chooses between two answers: Q is told only where its own
    comment names `Row` and `Row` is removed or renamed, or Q is always told, which is one job per passer, not per
    passer's user.
  - A user of `q: rows` that never reads `Row` is not told. If it hands the rows further, to V, then V's file names
    `p: Row via u: …` and V is told.
- **(b) Keeping it accurate.** The route makes the record checkable from files alone: U's `via q: rows` must match
  Q's `rows hands on p: Row`. The tool can compare the two in milliseconds, and the language reader can confirm the
  pair where typed. When Q changes where `rows` comes from, Q's line changes; or, where typed, Q's listing does. That is
  a change to what `q: rows` hands back, so by the existing rule it tells U, which names `q: rows`. U's job then
  updates its record. So staleness comes back to the user through a rule that already exists, and no new mechanism is
  needed. The cost: a passer's job must write its hands-on lines, one per entry that hands on another module's kind.
- **(c) Passers multiplier.** None from the passers' users. At most one notice per passer.

### Option D. Both, each a telling key (both propagate)

U names both. A change to `Row` tells readers of `Row` and, by propagation, every user of `q: rows`.

- **(a)** The union of A and C: the most told. **(b)** The most bookkeeping. **(c)** The full multiplier, as A.

### Recommendation: C

- **It is the owner's rule taken literally.** "The users of the entry that changed" are the modules that use `Row`, not
  those that call something whose answer contains a `Row`.
- **It removes the passers multiplier where it does harm.** Combined with F1, that multiplier turned one description
  into 164 changed listings. Under C a passer is at most one notice.
- **It stays accurate through a rule that already exists.** A change of origin inside Q is a change to Q's entry,
  which tells U.
- **The job's work is bounded.** It reads Q's hands-on line, not Q's code. Where typed, the reader can check the pair.
- **The open choices for the owner**:
  - whether a pure passer is told of a shape change to a kind it only hands on;
  - whether a changed data row or data file (C4, D1) counts as a change of range.
- **Risk.** A user that reads `Row`'s fields through a computed key, a spread, or a value it got untyped and never
  traced, and writes no record, is missed. The user's tests or a walk catch it, as the design accepts.
