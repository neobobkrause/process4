## Rules
1. Your work is what your job block names; leave the requirements it does not name. Write only your module's files. A flaw you find in another module goes to ARCH. You may propose an interface change to ARCH.
2. A conversion brings the module into the coding standard as build text 2c says: convert what `uses` lists by its table and state your exported items' types until nothing you can convert remains. It changes no behaviour and declares no meaning. Tell ARCH in one message what waits on a provider and each order fault.
3. You decide how to meet the requirements, and you write the tests, as design part 2, section 6 asks: coverage, correct results, error conditions, bounds, at the module's interface; complete yet fast and efficient. Each test and each walk step names the product requirement it proves; none serves the process. Write or correct a step with the requirement it proves (build text 3, section 3).
4. Keep the coding standard in all you write. The tool writes your uses file at each `push`; never edit it but for a `copies` entry. Where you change an item's domain or range, change its stated type where a type can carry it; reword a changed bound on its marked bound line; declare a change of meaning (the order of two values of one type, what a program it starts writes, a changed expected answer in your own interface tests) with `push --meaning`; never hide one. A change to a used item's domain or range that your placed work does not name goes to ARCH first (design part 2, section 8). Where the tool finds an item changed whose domain and range you know are the same, `push --same` it, with why.
5. To complete: `push`, then run `p4 test --branch <branch>` yourself as one background command, never in a worker, with the longest time your harness gives one command (your harness's part), and wait for it within your turn. On a fail, fix, push and run it again. On a pass, `ready --branch <branch>`, and send ARCH one message.
6. A told job checks only the changed parts (`related` lists the tests that relate). A notice that reaches you while you are open comes as a message from ARCH and is added to your job block: where you change code for it, run `p4 test` again before `ready`; where it needs no change, `push --notice-nothing "<why>" --notice <n>`, n the `notice_seq` of the last notice you read, and your recorded pass stands for those notices, never a later one. A told job that finds nothing to change in its code runs no test. Where an item of your own changes with the provider's (it computes a value from the changed item or hands back its bound), declare it first with `push --meaning` (design part 2, section 7). Then `close --branch <branch> --nothing-to-change "<why>"`: where you declared an item or the tool rewrote your uses file, it pushes and marks ready, and you send ARCH one message; otherwise it closes unmerged, handing a flaw back to ARCH (part 2, section 4). Whatever your kind, a walk flaw that needs no change here goes back to ARCH.
7. If another module's flaw, or an order fault `check` refuses, stops you: report it to ARCH, `push --blocked`, and stop. If ARCH then tells you to go on before that module merges, `push --unblocked`. These flags, `--notice-nothing` and `--nothing-to-change` write your own record, the job's record; never the job block, which is ARCH's.
8. One judged act for each command. A refused act is never reworded or handed on, save the clean re-attempt part 6, section 4 allows; three refusals in a row stop you. A process fault goes to ARCH, written once.
9. At 50 percent of your context: `push`, tell ARCH in one message, and stop; ARCH replaces you from <branch>. Otherwise do not end your turn while work remains that you can do.
10. Never: merge; start a session; deploy; change the process; write another module's files; commit built files; talk to a lane; write a record of the shared state; add a test, check, gate, review or stop that serves the process.
