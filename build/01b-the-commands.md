# Process4 build text 1b: the tool's commands

Section 4 of build text 1, kept in its own file so that each stays under 24,000 bytes; its number is kept. Sections 1 to 3 and 5 to 8 are in `01-the-tool-and-the-required-run.md`, whose sources hold here. Where this text and the design (`design/`) differ, the design rules. **Status: proposed. The tool is built and its own tests pass, but it has not run in a process in force; nothing here is proven in a running process, and nothing is in force.**

Marks: **Decided here:** a choice of this text, with what it gives and costs; the owner or PROCESS can overrule any. **Unproven:** never shown to work.

## 4. The commands

One for each act in part 6, section 5. Common to all: arguments are checked for form only; a command prints plain lines and ends with `ok` or one line `p4 <command>: <what failed>, in GitHub's own words where GitHub refused`; exit code 0 or 1. A refusal by GitHub is printed and never retried by another route. The tool cannot message a session: where the design says "the tool tells ARCH", the tool prints the line and the session sends it. No command refuses work for size. None adds a check, gate, review or stop beyond those the design names: `test` runs a pull request's module tests on its head brought up to the base, `ready` and `merge` read the test record it writes (part 2, sections 3 and 6), and `merge` waits for the open jobs of the modules a job uses (part 2, section 8). `ready`, `close`, `results` and `test` name a pull request by its number, or by a branch (`--branch <b>`, else the current branch): that branch's open pull request, or where none is open its newest in any state. A job on a detached checkout names `--branch <its branch>` or the number.

1. **`branch <name> [--into <branch>]`**. Makes branch `<name>` from the newest commit of the branch the process config names (the tranche branch; in the process's repository, `main`), or of the branch `--into` names; with no process config and no `--into`, of the repository's default branch; with one empty commit so that a pull request can open (unproven), and pushes it. Prints the branch and commit id. If the branch exists, says so and ends `ok`. A job's branch is `job/<module>.<n>`, n counting from 1: one more than the number of that module's earlier job pull requests, which `next-job` works out and prints. A branch `job/<module>/<n>` is also read as a job's branch, and counted. Other work is `work/<what>`. Gives: the run reads the module from the name, and each job of a module starts from the newest commit. Costs: earlier branches stay.
2. **`push [--blocked <module> "<why>" | --unblocked "<why>"] [--meaning <item> "<was; is now>"]... [--same <item> "<why>"]... [--notice-nothing "<why>" [--notice <n>]]`**. First rewrites, as `uses` does (command 28), the uses file of each module whose code or tests the branch changes against its base (a job's: its own module only; with no uses file yet, its first), and, where the branch changes the module list, of each module it touches and each user whose uses file names a moved or renamed item; commits any whose content changed (part 2, sections 7 and 9). A change to the facility list or to the process config's `process` version rewrites none (build text 2c). Then pushes the current branch's commits to the same-named branch, never the tranche or main branch, never forced. Prints the commit id pushed. With `--meaning`, also writes that line into the pull request's meaning comment (build text 5, section 5); with each `--same`, that item and why its domain and range are the same, into the same comment, so the item tells no one (part 2, section 7). With `--notice-nothing`, also writes `notice_needs_no_change` into the job's record alone: the why, and the count it answers, `--notice <n>` (the last notice read, not above the block's `notice_seq`), else the block's `notice_seq` then; the recorded pass stands for those notices, never a later one (build text 5, section 5). With `--blocked`, also writes the blocking module and the reason into the job's record on its pull request (see `close`); when that module merges the job is ready again. With `--unblocked`, rewrites that record to `{ "unblocked": "<why>" }`, where ARCH ended the block by its own decision and told the job to go on; the job is then open and holds its slot. On GitHub's refusal prints it and exits 1.
3. **`open --module <name>`** or **`open --title "<t>"`**. Opens a draft pull request from the current branch into the branch the config names (`--into-main` for the tranche's own; `--into <branch>` for another branch, as for `branch`). From a detached checkout it names the branch with `--branch <b>`. For a job it writes the job block (build text 5, section 5): the module, the work placed, the kind, the items ARCH named as changing meaning, and the uses any notice carries, read for each notice waiting for the module from the notice comments on the merged provider's pull request that the waiting-work entry names (build text 5, section 5). For a conversion the block's work is the conversion alone, and the module's other waiting work stays in waiting work. Where the round record holds the tranche's scope (build text 5, section 2), only the requirements it names go into the block, and the module's other requirements not yet met are listed under `not_this_tranche`. The kind is `conversion` where the module's conversion is its work; otherwise `told` only when notices are the module's only work, and with other work as well `ordinary`, the block still carrying the uses (part 2, section 7). Only ARCH's session writes it. It then prints the number, the address, and the job's starting instructions: the job text of `starting_texts/` filled in with names and addresses only (part 4, section 11): the fetch line, the module, the branch, this pull request. The block is cut to fit (build text 5, section 5) before anything opens. If one is open already, prints the same and the job block, first writing the block where it has none; so a job reads its work, kind and uses. The order (part 4, section 11): `next-job` chooses; ARCH's session runs `branch` and `open`; then it starts the job's session with that text.
4. **`ready [<pr>] [--branch <b>]`**. Runs nothing. Where the pull request is ready already, merged or closed, says so, marks nothing and ends `ok`. Otherwise marks it ready, and reads it back, only where its test record stands for the head commit, or the scope is nothing (build text 1, section 5) and no record is needed, as build text 5, section 5 says from the job block and the job's record (command 27). Otherwise marks nothing, prints why (`run p4 test`) and exits 1. On a conversion job, once marked, it writes the conversion's report on the pull request (build text 5, section 5). In the process's repository pull requests go into `main`, so the scope is nothing.
5. **`close [<pr>] [--branch <b>] [--nothing-to-change "<why>"]`**. With the flag, first writes the job's record: `nothing_to_change`, and where notices reached the job `notice_needs_no_change` at the block's `notice_seq`. Then it rewrites the module's uses file as `push` does (command 2), pushing it where it changed. Where the pull request declares by `push --meaning` an item of the job's own that changes with a provider's (part 2, section 7), or the uses file differs from its base's, it marks the pull request ready with no test run and prints that ARCH merges it; that merge tells the declared item's users. Otherwise it closes unmerged (part 2, section 7). Without the flag it closes unmerged. The job's record is a comment of its own, written only by the job's session, here and by `push` (build text 5, section 5). Each comment has one writer (part 4, section 11).
6. **`merge <pr>`**. Reads the standing notes; if the owner holds this merge, prints that and exits 0 without merging (his hold, not a check). For a job's pull request it then reads the job block, the job's record and the test record:
   - Where the block's notice count is above what the test record and the job's record answer (build text 5, section 5), prints `a notice reached <module>'s job after its tests ran; it must run p4 test again` and exits 1 (part 2, section 6).
   - Where a module this module uses has an open job not recorded blocked, prints `waits for <module> (pull request <n>)` for each, merges nothing and exits 0 (part 2, section 8). The modules it uses are the providers its uses file names, then theirs in turn, read at both the tranche branch's newest commit and the pull request's head; a module with no uses file yet waits on the earlier modules its code and test files import. No language reader is loaded.

   Otherwise asks GitHub to merge with a merge commit, guarded by the head commit id. Apart from the notice count, whether the required run has passed is GitHub's rule, which the tool does not repeat. Prints the merge commit, or GitHub's refusal. In the process's repository pull requests go into `main`, and only PROCESS runs `merge`, on the owner's word.
7. **`release prepare <version> --notes <file> [--file <built file>]...`**. Makes an unpublished release on GitHub at the main branch's newest commit, with the notes and files given. Prints its address. With `--development` it makes a development release: a pre-release with its tag, in the product's repository.
8. **`release publish <version> --approval "<the owner's words>"`**. Publishes that release and prints the address. The words are printed back and not judged by the tool. **Unproven:** both, and that the checker passes them (part 3, section 6).
9. **`next-job`**. Reads the round, waiting-work and standing-notes records, the module list and GitHub's open pull requests. A module is ready when it has work and no open job; a module none of whose conversions has merged has its conversion as work (part 2, section 3); where the round record holds the tranche's scope, a requirement not yet met, or a conversion, is work only where the scope names it (build text 5, section 2), so a module whose requirements all wait has none, and counts as finished for the round. Picks the earliest in module order, after any module the owner put first, if a slot of the product's share is free. With no slot free, a module with a notice waiting and no open job, earlier in the order than the latest running (open, not blocked) job's module, starts above the slot number, and the command says so; a later one waits its turn and is named. A job ready again after a block, and work other than a notice, start only below the slot number. Slots in use are the product's open job pull requests not recorded blocked, plus its live walking sessions in the round record. Rewrites the round record, and prints the module, its branch's name, its work and its kind (`conversion`, `told` or `ordinary`); `open` then prints its starting instructions. Prints `none ready` or `no free slot` otherwise. **Decided here:** one job for each call. Gives: one judged act for each start. Costs: eight calls to fill eight slots.
10. **`listing <module> [--at <commit>]`**. Writes the product's files at that commit (the current branch's newest if none is given) into a folder outside the working tree, and prints each item's means: the module's interface listing, a message kind's channel among it, made with the reader's checker from the interface files its entry names (build text 2b, section 6), and the parts worked out from its code (build text 5, section 6). Writes nothing to GitHub. **Unproven:** the folder made from a commit, and the parts worked out from code: built and tested by the tool's own tests, not run on a product.
11. **`notify <pr>`**. Run by ARCH's session after a merge, as its own background command of up to two hours; ARCH goes on merging other ready jobs meanwhile (part 2, section 3).
    - **What it reads.** It writes two folders at the same moment, the product at the merge commit's first parent (before) and at the merge commit (after). Which modules' files the merge changed it reads from the two module lists and the changed file names alone, and whether it changed a package's version (`package.json`, its lockfile) or the host's (the facility list); where it changed none of these it prints `The merge changed no module's files.` and reads no code. It sends one notice for each module whose files the merge changed, in module order, each telling a user once; so a user can be told once for each changed module (part 2, section 7). The pull request that takes the main branch into a paused tranche after an urgent fix is read as any merge.
    - **What changed.** For each changed module it works out each item's means before and after, from that module's files and its providers' stated types, adds the items the merged job block's `meaning` names and the pull request's meaning comment declares, and takes off each item that comment records as the same, unless named or declared (build text 5, sections 5 and 6). Each item that differs gets its words (build text 2b, section 6); only a change of its stated types or bounds tells (the owner's decision of 26 November; a program it starts: its start arguments and output), and a provider's error or channel taken in by a later module's item makes no item changed. Where no item changed it says so. A conversion's merge (the merged job block's `kind`) tells no one: `notify` says so, reads no code, and removes from the waiting-work record each notice waiting for that module (one rewrite, only where there is one).
    - **Who is told.** It reads the later modules' uses files, a lookup with no code read, and tells the modules of the design's points 1 to 4 (part 2, section 7), read from the uses files' fields as build text 5, section 6 says, once each; no module whose conversion has not merged is told, and the printout counts them. A module whose code or tests the merge changed is not told where the merged pull request's test record ran its whole tests on the merged result (its `modules`, build text 5, section 5). A new item tells no one, unless it changes what a name already used resolves to, by lookup: a name another module answers in the tables of operations, or one reached through a module that hands the provider on by `export *`.
    - **A told user with an open job,** blocked or not. The notice is added to that job's block: `notice from <provider> (pull request <n>)` to its `work`, the reasons to its `uses`, one to its `notice_seq`, and `{from, merged}` to its `notices`; its kind is left. The block stays under 60,000 characters, cut as build text 5, section 5 says. It prints `message the job of <module> (pull request <m>): a notice from <provider> reached it`, which ARCH's session acts on. Where the job's pull request merged or closed while its block was written, the user is treated as having no open job.
    - **A told user with no open job,** including one whose job merged before the notice was worked out. The reasons, its `uses`, are written once on the merged pull request, in the notice comments (build text 5, section 5), and the waiting-work record gets only the module, `notice`, the provider and the merged pull request, for the module's next job (part 2, section 7).
    - **No repeats.** A told user whose job pull request, open, merged or closed, already names this notice in its block is skipped, so a second run for the same merge adds nothing.
    - **Limits.** A write GitHub refuses ends with GitHub's own words, its message included. Where a reading does not fit the machine's memory it prints `p4 notify: could not read the product within this machine's memory; nobody is told; the notice for pull request <n> is owed` and exits 1. `listing`, `notify`, `check` and `uses` run with a memory allowance of three quarters of the machine's memory where node's default is less.
    - Prints the notice. **Unproven:** the two folders made from two commits; more than one changed module; the means and the lookup, which are built and tested by the tool's own tests but not run on a product.
12. **`finished <module>`**. Prints `finished` or `not finished` with the ground, worked out afresh from GitHub: its job's pull request merged, or closed with a nothing-to-change record (a notice-only told job, or one handing a walk flaw or job-reported flaw back to ARCH), provided the module has no unmet work.
13. **`round-done`**. Prints `done` or `not done`, and each module finished, open or blocked with its reason (part 2, section 4).
14. **`results [<pr>] [--branch <b>]`**. Prints whether the test record stands for the head commit (with the job's record) and what it holds (or, with no record, that none is needed, where build text 5, section 5 needs none), then the required run's state on the head commit (waiting, passed, failed), its address, and for a failed run the last lines of its output.
15. **`failed-runs <pr>`**. Prints the count of failed test runs on the pull request, the test record's `fails_total` (none counts 0), with no reset. At the third it also prints the line for ARCH to replace the session; at the fifth, the line that the module is to be recorded blocked (part 4, section 10).
16. **`state read [<record>] [--repository <address>]`**. Finds the issue by its label, lists its comments in one call, prints the record or all of them. With the flag it reads another repository's issue, where the harness allows it; a product's session cannot read the process repository's so, and the coordinator finds PROCESS in its own roles record instead (build text 5, section 4).
17. **`state write <record> --from <file>`**. Rewrites that record's comment in place, or its comments where it outgrows one; `--create` makes the issue and its empty records once (ROOT in a product, PROCESS in the process's repository). It removes each standing note whose ending has come true, and refuses a second live session for a lane (the design's own refusal). The label, the marks, each record's fields and writer, what ends each note, and a failed write are in build text 5 (`05-the-records-and-following.md`), sections 1 to 4.
18. **`check <module> [--files <list>]`**. Inside module tests (part 2, section 6). Three parts, each printed with file and line:
    - Declared uses against the order: the providers the module's uses file names, which the tool writes from its source and tests (command 28); for a module with no uses file yet, the modules its code and test files import. A use of a module that is not before this one in the order disagrees. A place outside the coding standard that may refer to a later module is "cannot tell".
    - Each structured comment against its code.
    - The module's code against each provider's stated interface.

    Exit 1 if any disagrees. Where the reader cannot tell, it says so and does not refuse. A complaint of the reader is a disagreement only where a structured comment states what it contradicts, a mark of this module (build text 2b, section 5) or a provider's stated interface, and for a value handed across only the comment on the side that receives it (build text 2b, section 5), or where an import names what a file of another module does not export; on plain code it is "cannot tell". A wrong-typed value a test passes on purpose inside an error assertion (`assert.throws`, `assert.rejects` and their kin) is "cannot tell", not a disagreement, so an error-condition test is never refused for it. Files `language_reader.exclude` names are not read (build text 2, section 7). A file holding an expression nested too deeply for the reader to follow is "cannot tell" for that file, never a crash or a refusal. **Unproven:** that it refuses only real disagreements.
19. **`walk open <internal|external>`**, **`walk close <issue>`**. Opens the walk issue, titled with the tranche, round and kind of walk, and writes its number in the round record; closes it when ARCH has placed every entry (build text 3, section 6).
20. **`walk write <issue> --session <n> --from <file>`**. A walking session's one comment in the walk issue, under its hidden mark (the session's number), rewritten in place. The session knows its own number, filled into its starting text.
21. **`walk read <issue> [<flaw>]`**. Prints the issue's comments, or one flaw, for ARCH and for the job given a flaw.
22. **`walk text <session>`**. Prints a walking session's starting instructions (part 4, section 11): its text filled in with names and addresses from the round record and the config. Its areas stay in the round record, which the text names.
23. **`walk areas`**. Lists the modules a round changed and the areas they name, for ARCH to choose from (part 6, section 5): the pages and journeys their step headers and requirement text name (build text 3, section 2; build text 2, section 4).
24. **`related <pr>`**. Lists a told job's related tests, as step 5 of build text 1, section 5 picks them (a line changed in comments or layout only is not changed), each with what put it in the list, and the files left out; `test` runs them. It only lists; it runs nothing.
25. **`latest-version`**. Reads only. Prints the newest commit of the process repository's main branch — the version a move to the latest adopts — from the address the process config names, and whether it differs from the pinned commit. ARCH runs it so a version move needs no commit id from the owner. How a move is made is in build text 2, section 7. **Unproven:** the read of another repository's main from a session.
26. **`drop --tranche <name>`**. ARCH's session, when the owner has dropped a tranche (design part 3, section 5). Makes branch `drop/<name>` from the tranche branch's newest commit and puts back the main branch's version of every file that differs between the two and that a module's `files` or `tests` paths own, by either branch's module list, and each such module's uses file; a file the main branch lacks is deleted. Each module's requirements file, the module list, the process config and the lanes' folders are left as they are. Commits, pushes, opens the pull request into the tranche branch, and prints its number and how many files were put back and deleted. Refuses, in one line, when `drop/<name>` already exists, when nothing differs, or when the tranche branch cannot be found. ARCH then runs `ready` and `merge`; the required run passes it at once only where every changed file is the main branch's (build text 1, section 5, step 4).
27. **`test [<pr>] [--branch <b>]`**. Run by the job's session, or by ARCH's for a pull request that is not a job's and changes module code or tests, as one background command of up to two hours (build text 1, section 5). Refuses a checkout with changes (`commit first`) or not at the pull request's head (`push first`). It first brings the head up to the base's newest commit as build text 1, section 5 says, pushing the merge as `push` does, uses file and all. Decides the scope on the merge of the head into the base's newest commit, then runs each module's `check` and its tests in scope in the session's checkout, printing each module as it starts and ends. Writes or rewrites the test record (build text 5, section 5); after a pass asks GitHub to run the head's newest required run again, saying so in one line where none exists or it is refused. Exit 1 on a fail, with the last lines of the failing module's output.

28. **`uses <module>`**. Reads the module's code and tests with the reader's checker under the coding standard's settings (build text 2c) and its providers' stated types, writes its uses file into the checkout, and prints what a conversion's first step lists: every reference in standard form, by provider and item; every place outside the standard, with its rule and the modules it may refer to; every order fault; every literal exactly equal to a value an earlier module offers; and what a conversion needs from a provider first. A note on a Node or workerd facility the tool does not know it prints, marked, and does not write (build text 2c). It keeps a `copies` entry for a JSON file as it stands. Writes nothing to GitHub. **Unproven:** all of it on a product; it is built and tested by the tool's own tests.

**The run's entry.** The workflow calls `p4.mjs run verdict` (build text 1, section 5), on GitHub's machines only, with `--job-block`, `--job-record` and `--test-record` naming the files it wrote. It is the tool's one `run` command.
