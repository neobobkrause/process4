## 4. The commands

One for each act in part 6, section 5. Common to all: arguments are checked for form only; a command prints plain lines and ends with `ok` or one line `p4 <command>: <what failed>, in GitHub's own words where GitHub refused`; exit code 0 or 1. No command refuses for size, and none adds a check, gate, review or stop. A refusal by GitHub is printed and never retried by another route. The tool cannot message a session: where the design says "the tool tells ARCH", the tool prints the line and the session sends it.

1. **`branch <name>`**. Makes branch `<name>` from the newest commit of the branch the process config names (the tranche branch; in the process's repository, `main`), with one empty commit so that a pull request can open (unproven), and pushes it. Prints the branch and commit id. If the branch exists, says so and ends `ok`. A job's branch is `job/<module>.<n>`, n counting from 1: one more than the number of that module's earlier job pull requests, which `next-job` works out and prints. It is one flat name under `job/`, so it never meets a branch named `job/<module>` that a product kept from an earlier process, which GitHub cannot hold beside `job/<module>/<n>` (the owner's decision of 23 Nov 2026). The earlier form `job/<module>/<n>` is still read as a job's branch, so earlier jobs and their numbers count. Other work is `work/<what>`. Gives: the run reads the module from the name, and each job of a module starts from the newest commit. Costs: earlier branches stay.
2. **`push [--blocked <module> "<why>" | --unblocked "<why>"]`**. Pushes the current branch's commits to the same-named branch, never the tranche or main branch, never forced. Prints the commit id pushed. With `--blocked`, also writes the blocking module and the reason into the job's record on its pull request (see `close`); when that module merges the job is ready again. With `--unblocked`, rewrites that record to `{ "unblocked": "<why>" }`, where ARCH ended the block by its own decision and told the job to go on; the job is then open and holds its slot (the owner's decision of 23 Nov 2026). On GitHub's refusal prints it and exits 1.
3. **`open --module <name>`** or **`open --title "<t>"`**. Opens a draft pull request from the current branch into the branch the config names (`--into-main` for the tranche's own). For a job it writes the job block (build text 5, section 5): the module, the work placed, the kind, and the uses any notice carries: for each notice waiting for the module, read from the `<!-- process4-notice -->` comments on the merged provider's pull request that the waiting-work entry names (build text 5, section 2). Where the round record holds the tranche's scope (build text 5, section 2), only the requirements it names go into the block, and the module's other requirements not yet met are listed under `not_this_tranche`. The kind is `told` only when notices are the module's only work; with other work as well it is `ordinary` and the block still carries the uses (part 2, section 7). Only ARCH's session writes it. It then prints the number, the address, and the job's starting instructions: the job text of `starting_texts/` filled in with names and addresses only (part 4, section 11): the fetch line, the module, the branch, this pull request. If one is open already, prints the same and the job block; so a job reads its work, kind and uses. The order (part 4, section 11): `next-job` chooses; ARCH's session runs `branch` and `open`; then it starts the job's session with that text.
4. **`ready [<pr>] [--branch <b>]`**. Runs nothing. Where the pull request is ready already, merged or closed, says so and marks nothing (the owner's decision of 25 Nov 2026); `--branch` finds the branch's newest pull request in any state where none is open. Otherwise marks the pull request ready, then reads it back, only where its test record stands for the head commit (a pass at that commit, made after every notice its job block holds; command 27), or where the scope is nothing (build text 1, section 5) and no notice has reached the job; a told job always needs its record, even with an empty related list. Otherwise marks nothing, prints why (`run p4 test`) and exits 1 (the owner's decision of 24 Nov 2026). The pull request is named by its number, by `--branch <b>`, or, with neither, the current branch's one open pull request; a job on a detached checkout names `--branch <its branch>` or the number (the owner's decision for fault o, 19 Nov 2026). In the process's repository pull requests go into `main`, so the scope is nothing and `ready` marks them as before.
5. **`close [<pr>] [--branch <b>] [--nothing-to-change "<why>"]`**. The pull request is named by its number, by `--branch <b>`, or, with neither, the current branch's one open pull request; a job on a detached checkout names `--branch <its branch>` or the number. With the flag, first writes the words into the job's record; then closes unmerged. The job's record is a second comment, written only by the job's session, here and by `push --blocked` (build text 5, section 5). Each comment has one writer (part 4, section 11).
6. **`merge <pr>`**. Reads the standing notes; if the owner holds this merge, prints that and exits 0 without merging (his hold, not a check). For a job's pull request, then (the owner's decision of 24 Nov 2026): where its job block's notice count is above its test record's, prints `a notice reached <module>'s job after its tests ran; it must run p4 test again` and exits 1; and where a module this module uses has an open job not recorded blocked, prints `waits for <module> (pull request <n>)` for each, merges nothing and exits 0. The modules it uses are the earlier modules its code and test files import, followed file to file as the notice's staged reading follows them (relative paths, `require`, the product's own package name), and those it declares, then through their own uses in turn, read at both the tranche branch's newest commit and the pull request's head. No language reader is loaded. An import the scan cannot follow, such as a computed one, is not waited on. Otherwise asks GitHub to merge with a merge commit, guarded by the head commit id. GitHub's rule decides whether the required run has passed; the tool repeats none of it. Prints the merge commit, or GitHub's refusal. In the process's repository pull requests go into `main`, and only PROCESS runs `merge`, on the owner's word.
7. **`release prepare <version> --notes <file> [--file <built file>]...`**. Makes an unpublished release on GitHub at the main branch's newest commit, with the notes and files given. Prints its address. With `--development` it makes a development release: a pre-release with its tag, in the product's repository.
8. **`release publish <version> --approval "<the owner's words>"`**. Publishes that release and prints the address. The words are printed back and not judged by the tool. **Unproven:** both, and that the checker passes them (part 3, section 6).
9. **`next-job`**. Reads the round, waiting-work and standing-notes records, the module list and GitHub's open pull requests. A module is ready when it has work and no open job; where the round record holds the tranche's scope, a requirement not yet met is work only where the scope names it (build text 5, section 2), so a module whose requirements all wait has none, and counts as finished for the round. Picks the earliest in module order, after any module the owner put first, if a slot of the product's share is free. With no slot free, a module with a notice waiting and no open job, earlier in the order than the latest running (open, not blocked) job's module, starts above the slot number, and the command says so; a later one waits its turn and is named (the owner's decision of 24 Nov 2026). A job ready again after a block, and work other than a notice, start only below the slot number. Slots in use are the product's open job pull requests not recorded blocked, plus its live walking sessions in the round record. Rewrites the round record, and prints the module, its branch's name, its work and its kind; `open` then prints its starting instructions. Prints `none ready` or `no free slot` otherwise. **Decided here:** one job for each call. Gives: one judged act for each start. Costs: eight calls to fill eight slots.
10. **`listing <module> [--at <commit>]`**. Writes the product's files at that commit (the current branch's newest if none is given) into a folder outside the working tree, and runs on it what the proof ran as `listing <product folder> <module>`: the module's interface listing, made with the reader's checker from the interface files its entry names (build text 2b, section 6). Prints it; writes nothing to GitHub. **Unproven:** the folder made from a commit; the proof was given folders.
11. **`notify <pr>`**. Run by ARCH's session after a merge, as its own background command of up to two hours; ARCH goes on merging other ready jobs meanwhile, and a user merged before the notice is worked out has no open job then, so its notice waits for its next job (the owner's decision of 25 Nov 2026). Writes two folders at the same moment, the product at the merge commit's first parent (before) and at the merge commit (after), and runs on them what the proof ran as `notice <before folder> <after folder> <module>`. Which modules' files the merge changed it reads from the two module lists and the changed file names alone; where none changed it prints `The merge changed no module's files.` and reads no code (the owner's decision of 23 Nov 2026). **Decided here:** once for each module whose files the merge changed, in module order. Gives: a mechanical edit across modules is covered. Costs: a user can be told twice. The notice compares the listings of the module and of every module after it, entry by entry. If none differ it prints `The listing before and after is the same. Nobody is told.` Otherwise it gives each entry that differs the proof's words; "accepts more" tells nobody only where the type checker confirms it (build text 2b, section 6). It finds the users of each such entry in every later module, declared or not; a user not followed fully is told on any change to the listing (build text 5, section 6). For a told user whose job pull request is open, blocked or not, it adds the notice to that job's block instead: `notice from <provider> (pull request <n>)` to its `work`, the reasons to its `uses`, one to its `notice_seq`, and `{from, merged}` to its `notices`, leaving its kind; and prints `message the job of <module> (pull request <m>): a notice from <provider> reached it`, which ARCH's session acts on. A second run for the same merge adds nothing. For every other told user it writes the reasons, its `uses`, once on the merged pull request, in `<!-- process4-notice -->` comments each under 60,000 characters, as many as needed, and adds to the waiting-work record only the module, `notice`, the provider and the merged pull request, for the module's next job (part 2, section 7; the owner's decisions of 24 Nov 2026 and B of 25 Nov 2026). A user it cannot follow fully is told only of a change that tells any user (build text 5, section 6). A write GitHub refuses ends with GitHub's own words. It reads in stages (the owner's decision D of 23 Nov 2026): each changed module's listing before and after from a reading of that module's files and what they import; where the listing is the same, nobody is told and no later module is read; otherwise only the later modules that can reach it are read, several to a reading (the owner's decision B of 25 Nov 2026), on the before side, and on the after side only where a changed entry is new or operations or tables are in play; the kinds a file declares are worked out once for each side and kept across those readings: those whose imports, followed file to file, lead to it, those that declare it, those that reach a carrier where operations or tables are involved, and those with an import the scan cannot follow. Where a reading still does not fit the machine's memory it prints `p4 notify: could not read the product within this machine's memory; nobody is told; the notice for pull request <n> is owed` and exits 1. Prints the notice. `listing`, `notify` and `check` run with a memory allowance of three quarters of the machine's memory where node's default is less, since reading a whole product twice needs more on a large product (the owner's decision of 23 Nov 2026). **Unproven:** the two folders made from two commits; more than one changed module, where the proof ran one at a time; the checker confirming "accepts more" (design 8, not built).
12. **`finished <module>`**. Prints `finished` or `not finished` with the ground, worked out afresh from GitHub: its job's pull request merged, or closed with a nothing-to-change record (a notice-only told job, or one handing a walk flaw or job-reported flaw back to ARCH), provided the module has no unmet work (the owner's decision for item 12, 20 Nov 2026).
13. **`round-done`**. Prints `done` or `not done`, and each module finished, open or blocked with its reason (part 2, section 4).
14. **`results [<pr>] [--branch <b>]`**. The pull request is named by its number, by `--branch <b>`, or, with neither, the current branch. Prints whether the test record stands for the head commit and what it holds (or, with no record, that none is needed where the scope is nothing and no notice reached the job), then the required run's state on the head commit (waiting, passed, failed), its address, and for a failed run the last lines of its output.
15. **`failed-runs <pr>`**. Prints the count of failed test runs on the pull request, the test record's `fails_total` (none counts 0), with no reset. At the third it also prints the line for ARCH to replace the session; at the fifth, the line that the module is to be recorded blocked (part 4, section 10).
16. **`state read [<record>] [--repository <address>]`**. Finds the issue by its label, lists its comments in one call, prints the record or all of them. With the flag it reads another repository's issue; the coordinator reads PROCESS's record so (part 6, section 7).
17. **`state write <record> --from <file>`**. Rewrites that record's comment in place; `--create` makes the issue and its empty records once (ROOT in a product, PROCESS in the process's repository). It removes each standing note whose ending has come true, and refuses a second live session for a lane (the design's own refusal). The label, the marks, each record's fields and writer, what ends each note, and a failed write are in build text 5 (`05-the-records-and-following.md`), sections 1 to 4.
18. **`check <module> [--files <list>]`**. Inside module tests. Three parts, each printed with file and line: declared uses against the imports of the module's source and tests (an import by written path or by the product's own package name, made by `import`, `export ... from`, `import()`, `require()`, or a comment's `@import`; a computed one, or an own-name one it cannot follow, is "cannot tell"), and against the order, where a declared use of a module that is not before this one disagrees (the owner's decision, 22 Nov 2026); a declared use with no import seen is "cannot tell", since a use by path is not read (the owner's decision of 24 Nov 2026); each structured comment against its code; the module's code against each provider's stated interface. Exit 1 if any disagrees. Where the reader cannot tell, it says so and does not refuse. A complaint of the reader is a disagreement only where a structured comment states what it contradicts, a mark of this module (build text 2b, section 5) or a provider's stated interface, and for a value handed across only the comment on the side that receives it (build text 2b, section 5), or where an import names what a file of another module does not export; on plain code it is "cannot tell" (the owner's decision 3B, 22 Nov 2026). A wrong-typed value a test passes on purpose inside an error assertion (`assert.throws`, `assert.rejects` and their kin) is "cannot tell", not a disagreement, so an error-condition test (design part 2, section 6) is never refused for it (the owner's decision for fault D, 19 Nov 2026). Files `language_reader.exclude` names are not read (build text 2, section 7). A file holding an expression nested too deeply for the reader to follow is "cannot tell" for that file, never a crash or a refusal. **Unproven:** that it refuses only real disagreements.
19. **`walk open <internal|external>`**, **`walk close <issue>`**. Opens the walk issue, titled with the tranche, round and kind of walk, and writes its number in the round record; closes it when ARCH has placed every entry (build text 3, section 6).
20. **`walk write <issue> --session <n> --from <file>`**. A walking session's one comment in the walk issue, under its hidden mark (the session's number), rewritten in place. The session knows its own number, filled into its starting text.
21. **`walk read <issue> [<flaw>]`**. Prints the issue's comments, or one flaw, for ARCH and for the job given a flaw.
22. **`walk text <session>`**. Prints a walking session's starting instructions (part 4, section 11): its text filled in with names and addresses from the round record and the config. Its areas stay in the round record, which the text names.
23. **`walk areas`**. Lists the modules a round changed and the areas they name, for ARCH to choose from (part 6, section 5): the pages and journeys their step headers and requirement text name (build text 3, section 2; build text 2, section 4).
24. **`related <pr>`**. Lists a told job's related tests, as step 3 of build text 1, section 5 picks them; `test` runs them. It only lists; it runs nothing.

25. **`latest-version`**. Reads only. Prints the newest commit of the process repository's main branch — the version a move to the latest adopts — from the address the process config names, and whether it differs from the pinned commit. ARCH runs it so a version move needs no commit id from the owner (the owner's decision C, 19 Nov 2026). A move is the process config's change by one pull request; where the new version's `shims/module-tests.yml` differs from the product's copy, the copy is replaced by a second pull request merged after the first, because the required run judges each pull request with the tool at the version its base names (the owner's decision B of 24 Nov 2026). **Unproven:** the read of another repository's main from a session.

26. **`drop --tranche <name>`**. ARCH's session, when the owner has dropped a tranche (design part 3, section 5; the owner's decision C of 24 Nov 2026). Makes branch `drop/<name>` from the tranche branch's newest commit and puts back the main branch's version of every file that differs between the two and that a module's `files` or `tests` paths own, by either branch's module list; a file the main branch lacks is deleted. Each module's requirements file, the module list, the process config and the lanes' folders are left as they are. Commits, pushes, opens the pull request into the tranche branch, and prints its number and how many files were put back and deleted. Refuses, in one line, when `drop/<name>` already exists, when nothing differs, or when the tranche branch cannot be found. ARCH then runs `ready` and `merge`; the required run passes it at once only where every changed file is the main branch's (build text 1, section 5, step 2a).

27. **`test [<pr>] [--branch <b>]`**. Run by the job's session, or by ARCH's for a pull request that is not a job's and changes module code or tests, as one background command of up to two hours (build text 1, section 5; the owner's decision of 24 Nov 2026). Refuses a checkout with changes (`commit first`) or not at the pull request's head (`push first`). Where the base branch holds commits the head lacks, merges the base's newest commit into the checkout with a plain merge commit and pushes it, so the tests run on code that holds what the base holds; where they do not merge cleanly, changes nothing, runs nothing and says to merge the base in first (the owner's decision B of 25 Nov 2026; not for a pull request into main or a drop's). Decides the scope on the merge of the head into the base's newest commit, then runs each module's `check` and its tests in scope in the session's checkout, printing each module as it starts and ends. Writes or rewrites the test record (build text 5, section 5); after a pass asks GitHub to run the head's newest required run again, saying so in one line where none exists or it is refused. Exit 1 on a fail, with the last lines of the failing module's output.

**The run's entry.** The workflow calls `p4.mjs run verdict` (build text 1, section 5), on GitHub's machines only. `run scope` and `run tests` remain, unused by the workflow.
