## 6. The means, and who is told: how the tool works them out

The rules are the design's (part 2, section 7); this section gives what the tool reads and its order (unproven: section 8).

- **The means**, before and after a merge, come from the provider's files and its providers' stated types, by the reader the process config names: the stated parts are the listing (build text 2b, section 6); a part reached through an owner's reader is that reader's stated types; a new type error in the item is a change. Only its stated types and bounds tell: the closure below decides plain data or an instance, `this`, and a started program's start arguments and output streams; the errors, other channels and arguments written into it also finds are listed and tell no one.
- **The closure, in order.** From the item's own pieces (a piece's text leaves out the pieces nested in it): (1) add by control each piece whose binding a piece names; each function, getter or setter member read, written or called by name, every function member for a computed access; a file named by a literal; a piece that runs when the piece holding it runs; an import's declaration and that file's top-level statements. (2) From every piece add its file's top-level statements and the order of its statements and imports; the implicit members, exactly `toString`, `valueOf`, `toJSON`, `then`, `next`, `return`, `throw` and `constructor`, and those with a computed name; and every piece, where a name resolves to nothing in the module. (3) Add the writers of every location a piece reads (a binding, a field by name, the contents of either, contents reached through a parameter, `this` or a call's result being one location, and the state outside the module), and each piece that reaches such a writer by control. Repeat until nothing is added.
- **Left out, as read.** A catch that never names its error covers what its try block raises and the code that block calls to run at once (not async, not a generator). A stream is standard output or error, or a message to the parent. The caller's input is a parameter with no default, or a `const` set from one. A module keeps no state when its files hold at top level only imports, functions, classes with no static state and `const` values made without running code, never written, written into or (a list or object) handed on; it writes only into what a function made fresh, and into `this` only in a constructor; it names no host facility that keeps state, and imports only such modules and Node's modules that keep none.
- **Who is told**, from the uses files (build text 2c), each read as the tool that wrote it meant it (a use without `value` is the whole value). A conversion's merge (the merged job block's `kind` is `conversion`) tells no one, and nothing is read but the waiting-work record, from which it removes each notice waiting for its own module. No module whose conversion has not merged (no merged job pull request of kind `conversion` for it) is told by any point; the printout counts them. Point 1: a use naming a changed item or a member of a changed kind, by any `route`, reached as its `value` says; a provider's error or channel a middle module's item takes in (`takesIn`) makes no item changed, and is not read. Point 2: a `marked copy` use, a `copies` entry, an S4 place whose `relabels` names the item. Point 3: an `outside` place whose `mayRefer` names the provider or is `*`; a `mock` use of it; an `orderFaults` entry naming it. Point 4: a `packages` entry for a package whose version changed in `package.json` or its lockfile, or for the host (`node`, `workerd`) whose version changed in the facility list. A new item tells no one, unless it changes what a name already used resolves to, found by lookup in the uses files and the providers' export lists, no user's code read: a name another module answers in the tables of operations (`<module> now answers the same name`), or a name reached through a module that hands the provider on by `export *` (`<provider> <name> now reaches it through a re-export`, with `resolves`); then that name's users are told. A module whose code or tests the merge changed is not told where the merged pull request's test record ran that module's whole tests on the merged result (`modules`, section 5).

## 7. A told job's related tests

The rule is the design's (part 2, section 7). The pieces are those of the files under the module's `files` and `tests`; a place belongs to the innermost piece holding its line; a call counts where the reader resolves it. The list is made on GitHub's merge of the pull request into its base, from the places the job block's `uses` names, out of the told module's uses file, and the lines the pull request changed. A `noUsesFile` or `whole` reason, and a reason that names no item (a `mock` or `package` reason), make every test file related, as does a module with no uses file; a line changed only in its comments or layout is not a changed line (the design, part 2, section 6); a file under `walk/internal/` or `walk/external/` never is. `related <pr>` prints each file with its cause, and the files left out; the test record's `why` counts them.
