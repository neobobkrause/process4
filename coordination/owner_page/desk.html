Waiting for you: the reworked design for who uses what

Bottom line. I recommend choice C: a standard for how code may refer to an earlier module, so that the tool itself finds every use with certainty, plus each job's marking of what it changed, against a list the tool makes so nothing is left off. Then the first pass on 8 real civicsmith modules, and a stop for you to judge.

Rigour from the language, as you asked. A helper worked from JavaScript's own definitions, not from samples. The language allows references no tool can find with certainty, such as module names built while the program runs, or code built from text. So "find every use in whatever code is written" has no rigorous answer, and "find every use in code written to a standard" does. The standard has 13 rules. Imports name the module in plain text. Another module's files and programs are reached only through that module's own functions. Lookups by name go through a declared table. Every item a module offers states what it takes in and hands back, checked by the type checker; that last rule is what makes a value passed on through a middle module traceable. Two of the 13 rules are already yours. Under the standard the tool writes each module's uses file itself, so it cannot go stale. Code not yet in the standard is listed as such, and is told of every change, as today, until a job brings it in. Nothing new stops a job.

Changes that must be told, from those that need not. Before a job finishes, the tool lists every item of its module that may have changed: its own code, anything it reaches inside the module, or its description. On all 150 recorded changes this list missed none of the items that really changed. The job then marks each item: changes what it takes in, changes what it hands back, accepts more only, or unchanged. A short guide in its instructions covers three facts of JavaScript that turn an inward-looking change outward, and the tool flags those cases. An item left unmarked counts as changed. On the 150: 1 missed, against 45 today. If every job marked nothing, nobody would be missed; more modules would be told.

Jobs that change no code run no tests, said at the top of their instructions.

Choice:

  • 0. No change. civicsmith cannot go on.
  • A. A file each job writes, without a standard. Rests on each job's care.
  • B. The standard without the rule that items state their types. The tool is certain for direct references; values passed through a middle module rest on the job.
  • C. The full standard (recommended). The tool is certain for every reference, except a few unsound corners of the type checker that are listed.

Not proven: how reliably real jobs mark their changes, and the cost of bringing civicsmith into the standard. Adding stated types to its modules is likely the largest cost, and it is unmeasured. The first pass measures both. If the types prove too costly, B is the fallback, and nothing already done is lost.

Waiting for you: sessions that sit idle are compacted

The question. Should sessions stop being compacted when they sit idle?

What happened. civicsmith's ARCH session lost what it had read. It was not because it filled up. It was 43 percent full, below the 50 percent point where it would hand over. It had been idle for 76 minutes, waiting on merges. When it woke, Claude Code shrank its memory to a summary. Claude Code's own notice said so: "Compacted using a summary written while you were away", and it names a setting that turns this off. Your design says refreshes must make compaction unnecessary, but it only knew about compaction when a session fills up. Any role idle for about an hour is exposed. ARCH is the most exposed, and ROOT wakes only hourly.

My own session showed the same.

  • 0. No change. Idle roles keep being compacted and carry on from a summary.
  • A. Turn idle compaction off. The setup script of the environment the sessions run in already writes one settings block for every session. It would also write "idleCompaction": false. I propose the change through Claude Code's own approval prompt, and you approve it with one click there. It applies to sessions started after that.
