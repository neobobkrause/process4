Waiting for you: the corrected design for who uses what

Bottom line. I recommend choice C, now corrected. Under the standard, every reference to an earlier module is found by the tool, or sits at a place the tool lists as not yet in the standard; such a place is told of every change until it is converted. Nothing is silently missed.

How the gaps were closed. The helper wrote 27 small test cases and ran each under two versions of the type checker. Under today's settings, each gap hid its reference and the checker said nothing. Under twelve added rules, every gap was found: 50 runs out of 50. Two ordinary cases raised nothing, so the rules do not flag good code. The rules, in plain words:

  • Nothing has an unknown type.
  • Data that comes from another module, through a file, a message, storage or the environment, is read only through that module's own reader, never relabelled by hand.
  • The tool itself checks every conversion between types, so it does not rely on the checker's known blind spots.
  • Nothing writes onto another module's values behind the checker's back, and nothing switches the checker off.

One setting the tool uses today, on caught errors, hides a reference now; it is turned the other way. What the result rests on: the type checker working as documented, the same trust we already place in reading imports at all.

Copies, as you put it: a bug. A module that writes out a value another module owns, such as a limit, a text or a name, has a bug. The rule: every fact is obtained from the module that owns it. A fact fixed in code is imported, which costs nothing at run time; a fact that is set or stored is read from its owner's reader, and any cache sits inside that reader, never as a copy in the module that uses it. Obtained that way, it is a reference, and found. Where obtaining is impossible, as in a test's deliberately written-out expected answer or a data file, it is marked with your naming convention and read as a reference. The tool also lists every literal exactly equal to a value an earlier module offers, to help the job. A breach of the rule is caught like any other bug, by the job, the module's tests and the walks; I do not claim the tool finds every bug, only every reference.

The rest stands as before. Before a job finishes, the tool lists every item that may have changed (it missed none of the 150 recorded changes), and the job marks each one by a short guide; an item left unmarked counts as changed. Who is told is a lookup. Jobs that change no running code run no tests. The first job on each module, run in parallel where order allows, does three things:

  1. It converts the module's references to the standard, and imports or marks its copies.
  2. It states the module's types.
  3. It lets the tool write the module's uses file.
